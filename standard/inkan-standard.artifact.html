Inkan · trust-signal seal standard v1.0

The Inkan Standard

A deterministic visual seal for data you must trust at a glance — an address, a signing key, a document. Its one job: a human notices when it changes. This document is self-contained and every seal below is rendered by the reference engine.

version 1.0 · frozen 2026-07-28 · revision 1.0.2 · extended-Golay coded · SHA-256 anchor · Python/JS/Kotlin byte-identical

§1  What an Inkan is

An Inkan is a permanent anchor and an open, versioned family of deterministic presentations.

The anchor is SHA-256 of a domain-separated seed over (data, kind) — 32 bytes, forever, and what a receipt commits to. The visual seal is a deterministic function of that anchor: the same anchor draws the same seal on every device, which is exactly what lets a person compare a wallet's seal against a signer's across an air gap. The digest is the anchor; the picture is a view. A new renderer is added beside the old one as a new version: it never invalidates an anchor and never changes an existing seal — that is the property that lets the standard last.

Why coded, not hashed-to-pixels. A naive visual hash bounds nothing: two seals may be arbitrarily similar. Inkan drives its structure with an error-correcting code, so any two distinct seals differ in at least 8 interior cells by construction — separation is a theorem, not an accident.

§2  Technical profile

LayerDefinition
AnchorGlyph seed inkan/v1\0 + u8(len(kind)) + kind + data, all text NFC-normalised, kind ≤ 255 B → SHA-256 → 32-byte digest. The length prefix makes the kind/data boundary unambiguous for any input.
CodeSelf-identifying ik1 + hex (ik=Inkan, 1=SHA-256/format v1), so a future hash migration (ik2…) is unambiguous. Short code = ik1 + 16 hex, a verifiable prefix used for filenames.
StructureInterior cells hold 2 bits, from bit-interleaved extended Golay [24,12,8] blocks (24/48/72-cell profiles). Minimum distance: ≥ 8 differing cells, tight, every profile.
SymmetryCk rotational symmetry, k = 1…7. Free cells are fixed per profile; only replication varies, so symmetry carries no entropy cost.
Colour32 classes × 5 roles, OKLab, separated by lightness (the channel that survives colour-vision deficiency), Brettel–Viénot–Mollon CVD-constrained, gamut-fit. Weighted selection down-weights classes resembling disfavoured third-party marks. Constant-weight core: exactly 2 of 4 cells inked, never uniform.
Canvas / PNG224 × 224 native, integer upscale for any size. 8-bit indexed, ≤ 5 flat colours. Canonical PNG carries no metadata; a tagged export embeds the ik1 code as an untrusted, cross-checked hint.
KindsOpen: any UTF-8 string, [namespace:]name[@tier]. Reserved kinds use a curated entry; any other string derives its geometry deterministically. No registry; third parties assign their own kinds and tiers.
ParityPython, JavaScript, Kotlin render byte-identically — float-free integer tables, proven over 1500 random cross-port vectors.

§3  Use matrix

The tier is chosen by exposure — what a mistaken seal costs — and is bound into the anchor via the kind, so it is not a user knob for reserved kinds. Higher tier = more cells = more visible entropy = a costlier forgery.

§4  Security audit

An adversarial audit was run to break the standard, not bless it. Result: no invariant failure. The measured facts:

≥ 8 / cells
Distance floor — verified tight (Golay min-weight 8 over all 4096 words; the floor is achieved, not merely bounded).
1500 / 1500
Cross-port vectors reproduced byte-for-byte by Python, JS and Kotlin — determinism proven, not assumed.
0 failures
Table integrity, avalanche (a 1-bit flip of the anchor moved ≥ 24 of 48 cells in each of 400 trials), statistics, and malformed-input robustness.
T1 unbroken
Perceptual lookalike grind: 12,000 attempts could not push a T1 seal below ΔE 0.063 — clear of the perceptual-identity line.

Measured facts, recorded honestly. Low-tier seals have findable perfect collisions — a 24-cell collision was ground in ~79,000 tries — because the seal is a deliberately lossy projection of the anchor (the digest, not the image, is what is trusted). Birthday cost is ~216 / 228 / 240 at 24 / 48 / 72 cells, which is precisely why value-at-risk kinds are 72-cell and the tier is enforced by the kind.

Honest limits. Every ΔE here is a model of perception, not a measurement of people — no human-perception study has yet run, and no accessibility or "phishing-proof" claim is made until it does. The frame motif is 6-bit (14 distinct frames per config); beyond that, open kinds may share a frame, which is defence-in-depth, not a break, since different kinds of the same data always differ in the interior.

§6  Forward provisions

Because the anchor is permanent and presentations are plural and versioned, the standard absorbs change without breaking a single existing Inkan: every change arrives as a new version beside the old ones (a new ik digit, a new SEAL_VERSION, a new canary record version), and no existing result changes. Reserved for the decades ahead: hash agility (the ik version digit), post-quantum signature agility (a record version that names its algorithm inside the signed bytes), extra tiers (@t0, @t4–@t9, which take effect only in a new seal version; under Seal v3 they are ordinary open kinds), and non-visual presentations of the same anchor — audio (an identity chime: cells→pitch, palette→timbre, kind→rhythm), 3D / physical (a height-map relief → a real stamp face or engraving, closing the loop on what a seal is), and haptic (a vibration pattern for wearables and accessibility). On-chain permanence, zero-knowledge verification, and a governance registry are reserved likewise.

§7  Verification & reproduction

Anyone can confirm an Inkan without trusting its source: recompute the canonical seal from the claimed (data, kind) and compare pixel-for-pixel. A lookalike fails because it is not the byte-exact render. The full 64-hex code is the anchor; the short code labels it.

§0  Permanence

These rules bind every revision of this text and every implementation that claims Inkan v1 (E17).

P1 Frozen results. For every input it accepts, Inkan v1 has exactly one result, forever: the anchor and its ik1 code (§1–§2); kind resolution under SEAL_VERSION 3 (the 14 reserved kinds and the suffixes @t1, @t2, @t3, §4); the Seal v3 pixels, fixed by the tables file with SHA-256 441881915ddf6c213dadac507d714b57068e0f6bb0a6f6070acd3fb924dcdf4b (§3.0) and by the CC0 vectors; each fingerprint version (§7); and the v1 canary record bytes and signature rule (§8).

P2 What an erratum may do. An erratum MAY clarify wording, add test vectors, or make implementations reject an input that was malformed or on which conforming implementations already gave different results. It MUST NOT change the result of any input that the reference implementation accepts and on which conforming implementations agree. One erratum is an exception, made in revision 1.0.1 before any canary record had been published: under E23's input rules, these canary records, on which the reference and the JavaScript verifier had agreed, now read MALFORMED: a record whose seq or block_height is negative, or is 2^53 or more and held exactly by a double, and a record read from wire bytes that are not its canonical bytes, all of which both read OK; and a record whose date is not a real time in the §8 form, which both read STALE. Every later erratum is bound by this paragraph without exception. Each revision of this text is numbered (1.0.1, 1.0.2, …), and the SHA-256 of each revision is published in SPEC-REVISIONS.md.

P3 Versions are new names, never edits. Every result belongs to a version: the anchor version ik<v> (one hash, domain "inkan/v<v>\0"), SEAL_VERSION, the fingerprint scheme, and the canary record version. No version name is ever reused or redefined. Where no marker is present, the result is ik1, SEAL_VERSION 3, the SHA-256 fingerprint, and record v1.

P4 Additive only. A new hash is a new anchor version with its own domain. A new seal design is a new SEAL_VERSION beside v3, never a replacement; its tagged PNG carries an inkan-seal keyword (§5), and a seal without one is v3. A product may choose which version it shows, but it labels it, and both sides of a comparison use the same version. The reserved suffixes (@t0, @t4–@t9) and new reserved kinds take effect only in a new SEAL_VERSION; under v3 they are ordinary open kinds (§4, E5). A new signature scheme is a new record version whose algorithm is named inside the signed bytes. An implementation that adds a version keeps generating, verifying and self-testing every earlier version it claims, and every conforming verifier keeps SEAL_VERSION 3.

P5 Explicit versions. A verifier treats the version as an explicit part of what it checks, never infers it from an untrusted tag, and reports an unimplemented version as UNSUPPORTED.

P6 Erosion. If SHA-256 or secp256k1 weakens, no v1 result changes. Verifiers keep computing v1 results and add a warning; migration adds the new version beside the old one.

E102026-08-04§6Integer-upscale downscaling MUST verify every pixel of each block, not sample one. The reference sampled the block's top-left pixel and never checked uniformity, leaving scale^2 - 1 pixels per block attacker-controlled — 98.44% of the image at scale 8. Demonstrated: an image 98.44% pixel-identical to one entity's genuine seal verified GENUINE as a different entity's. §6 already required "compare pixel-for-pixel"; it did not say the downscale had to be faithful, so a clean-room implementer would have inherited the hole. A non-uniform block MUST be a distinct failure, never a size error. Fixed in Python and in the built verifier page; JS and Kotlin have no presented-image path.
E112026-08-04§8A key or signature that does not parse MUST read MALFORMED, not INVALID. The reference collapsed both into INVALID — the maximum-severity verdict, which asserts a signature check ran and failed — for what is nearly always a truncated paste. This is the same principle E2 applied to unknown record versions: never report a check that did not happen as one that did. MALFORMED is fail-closed and is never OK. Fixed in Python and JS.
E122026-08-04§6A presented PNG carrying a rendering-affecting ancillary chunk MUST be rejected. tRNS names colours a conformant viewer must draw as fully transparent; gAMA/iCCP/sRGB/cHRM/sBIT/bKGD alter tone; acTL/fcTL/fdAT make it an animation. None change the decoded RGB, so a genuine seal plus one such chunk verified GENUINE while rendering differently — the same class of defect as E10, and demonstrated with tRNS. Benign metadata (tEXt, iTXt, pHYs, tIME) stays tolerated, so §6's re-encoding allowance is unaffected. Fixed in Python and in the built verifier page, the latter checking the file bytes rather than the canvas decode.
E132026-08-04§8A canary record MUST carry exactly the seven fields E1 fixes, with those types. Nothing validated this in any port, on either side of the wire. E212026-10-10§7The adopter-name profile of E6 is defined in terms that never change, and implementations MUST enforce it before hashing. E6 required a "printable" name with no NUL and no nkan/ prefix, but did not say what printable means, and no port enforced any of it: the name nkan/v1 + NUL + 97 × z makes the fingerprint preimage begin with exactly inkan/v1\0, so one digest is both a valid fingerprint and a valid anchor, the case E6 exists to prevent. E222026-10-10§7**A fingerprint version is a positive integer, and version n is SHA-256 over this construction forever.** Any value was accepted: 0 and −1 produced digests, and a fraction was truncated by one port and written out by another (version 1.5 gave the version-1 digest in Python and a different one in JavaScript). Such versions MUST now be rejected. A fingerprint over another hash gets its own domain and a self-labelled text form, never a new version number. Versions 1, 2, 3, … keep their results. Implemented in the Python and JavaScript fingerprints; the Python verifier and command line now take the version as an explicit input (default 1), as the JavaScript port and the web verifier already did. fingerprint-vectors.json pins both.
E232026-10-10§8A canary verifier MUST apply exact input rules, and report MALFORMED for a record that breaks one. The canonical bytes, the integer range, the date and string forms, and high-S were each left to the implementation, and the Python and JavaScript verifiers gave different verdicts on the same signed record: a seq above 2^53 that a double cannot hold exactly (2^53 + 1, or a nanosecond timestamp such as 1760112000123456789) read OK in Python and INVALID in JavaScript, which rounds it; 2026-6-30T0:0:0Z was fresh in Python and stale in JavaScript, hour 24 and second 60 the reverse; full-width digits were fresh in Python only; a statement holding an unpaired surrogate read OK in JavaScript and was mislabelled UNSUPPORTED in Python; and a key or signature written with a 0x prefix was read in JavaScript only, one with spaces between its digit pairs in Python only. §8 now defines the canonical bytes exactly, requires seq and block_height in 0 to 2^53 − 1, one ASCII date form that must name a real time, well-formed strings and canonical wire bytes, fixes the form of the key and signature as plain hexadecimal text, and requires high-S to read INVALID (as every port already reports it, though BRC-145 never said so). Every record that meets the rules keeps its verdict; no canary has been published. Some records on which both verifiers agreed also read MALFORMED now, because they break the rules: a seq or block_height of 2^53 or more that a double does hold exactly (2^53 itself, 10^18, a nanosecond timestamp in whole seconds), or a negative one, which both read OK; wire bytes that are not the record's canonical bytes, which both read OK; and a date that is not a real time in the §8 form (30 February, month 13, year 0000, a space in place of T, +00:00 or a fractional second in place of Z, blank space around it), which both read STALE. These records are the one exception §0 (P2) names. Implemented in the Python and JavaScript verifiers, which read a record either as an object (rules 1–3) or in its wire form (all four rules), and in the web verifier; the command line and the web verifier take a pasted or filed record as its wire form, ignoring only blank space around it. canary-vectors.json pins 33 cases, and both ports give every one its pinned verdict.
E242026-10-10§6A presented image MUST be a verifiable PNG (new §6.1), and only the chunks listed there are allowed. E12 listed forbidden chunks, and PNG keeps adding new ones: a genuine seal carrying cICP (a colour space) or eXIf (an orientation) verified GENUINE in the reference while a browser drew it in other colours or rotated. Nothing fixed which files a verifier accepts, so the reference accepted files browsers do not open as written (bad CRCs, no IEND, an unknown critical chunk, bytes after the end), and the web verifier, which let the browser decode the image, read GENUINE for files the reference rejected: an animated GIF named .png, RGBA, 16-bit, 4-bit-palette and interlaced images. §6.1 fixes the signature, the CRCs, an allow-list (IHDR, PLTE, IDAT, IEND, tEXt, zTXt, iTXt, pHYs, tIME), chunk order, the header (8-bit, truecolour or indexed, no interlace), the palette and image-data rules, and requires the verifier to decide on its own decode. Implemented in the Python verifier and in the web verifier, which now decodes the presented file itself under these rules, inflate included, and uses the browser only to display the result; png-profile-vectors.json pins 35 cases, and both give every one its pinned verdict.
